> **APP 名称**: engine-win-sync-builder

## 一、目标

构建一个多角色 APP（名称：`engine-win-sync-builder`），用于**自动将 Mac 验证过的 qoder-engine 仓库中的改进同步到 Windows 版引擎，并推送到目标 Git 仓库**。

该 APP 解决以下核心问题：

1. **Win 版代码获取**：Win 版引擎代码独立托管于 `git@github.com:xp-lv/qoder-engine-win.git`，需在同步前克隆到本地临时目录作为差异分析的基准
2. **差异检测**：当前 Windows 版 qoder-engine 与 Mac 验证版存在版本差异，需要系统性地识别所有差异点
3. **改进筛选**：并非所有差异都需要同步——有些是 Mac 特有代码（如 `.sh` 脚本），有些是 Win 特有代码（如 `.cmd` 脚本），需要精确筛选出"改进"而非"平台差异"
4. **平台适配**：Mac→Win 同步涉及路径分隔符（`/` vs `\`）、换行符（`LF` vs `CRLF`）、Shell 脚本（`bash` vs `PowerShell`）、环境变量等平台适配问题
5. **质量保障**：同步后的引擎必须在 Windows 环境下可正常运行（编译、调度、Gate 校验等核心功能不受影响）
6. **自动推送**：验证通过后自动推送到 `git@github.com:xp-lv/qoder-engine-win.git`

## 二、核心能力

| 能力域 | 描述 |
|--------|------|
| **需求接收与 Win 版代码获取** | 接收用户的同步需求，明确同步范围（全量/增量）、目标仓库地址、排除规则（如 `.sh` 文件不同步到 Win）。**从 `git@github.com:xp-lv/qoder-engine-win.git` 克隆 Win 版引擎代码到临时目录**（如 `{workspace}/win-repo-clone/`），作为差异分析的基准。产出结构化需求文档（含 Win 版克隆路径、commit hash） |

| **差异分类与改进评估** | 将每个差异分类为：(a) 改进（应同步）、(b) 平台差异（不应同步，如 `.sh` vs `.cmd`）、(c) 回退（Win 版比 Mac 版新，需谨慎处理）、(d) 无关变更（如 `.gitignore`）。只将 (a) 类差异标记为待同步。产出独立的改进评估报告（含差异分类结果、待同步改进清单、同步优先级） |
| **平台适配设计** | 对每个待同步的改进项，设计 Mac→Win 的适配方案：路径分隔符转换（`/`→`\`）、换行符规范（`LF`→`CRLF`）、Shell 命令替换（`bash`→`PowerShell`）、环境变量适配（`$HOME`→`%USERPROFILE%`）等。基于改进评估报告 + 差异红队对抗报告，产出同步设计文档 |
| **代码同步执行** | 按适配方案逐项修改 Windows 版引擎代码（克隆临时目录中的文件），产出变更摘要（每个变更项标注文件路径、修改内容、适配说明） |
| **回归验证** | 验证同步后引擎在 Windows 上的正确性：Python 语法检查、compiler.py 编译链路测试、DAG 可达性验证、Schema 校验、核心脚本可执行性检查、幂等性检查（重复执行同步操作不产生副作用）、引擎版本号一致性检查 |
| **Git 推送** | 将同步后的代码提交并推送到 `git@github.com:xp-lv/qoder-engine-win.git`，产出推送报告。**推送失败时自动重试**（最多 3 次，指数退避：1s/2s/4s），重试耗尽后标记失败并产出诊断报告 |
| **对抗性差异审查** | 差异红队从最恶劣条件挑战差异分析的完整性：是否有遗漏文件？是否有误分类？是否有隐藏的平台兼容性问题？ |

## 四、协作流程

**流程类型：迭代式（含对抗回路 + 质量回路 + 并行审阅）**

```
需求接收者 (producer, manual)
  │  ① 接收同步需求  ② 克隆 Win 版仓库到临时目录  ③ 产出需求文档
  │ confirmed
  ▼
差异分析者 ──────────── 逐文件对比 Mac(工作区) vs Win(克隆目录)，产出差异分析报告
  │ confirmed
  ▼
[FORK] 并行扇出 ──┬── 改进评估者 (维度：差异分类/改进筛选/同步优先级)
                 │     │ 产出：改进评估报告.json
                 │     └─ confirmed ─────────────┐
                 │                               │
                 └── 差异红队 (维度：完整性/准确性/遗漏检测/误分类检测)
                       │ 产出：差异红队-对抗报告.json
                       ├─ confirmed ─────────────┤
                       └─ challenged → 差异分析者 (backward, 修订差异分析报告)
                                       max_executions: 3
                                                   │
                                                   ▼
                                              [JOIN] 汇入
                                                   │
                                                   ▼
                                            平台适配者 ── 基于改进评估报告+红队报告设计适配方案
  │ confirmed
  ▼
同步执行者 ──────────── 按适配方案逐项修改 Win 版引擎代码
  │ confirmed
  ▼
回归验证者 ──────────── 验证同步后引擎在 Win 上的正确性
  │
  ├─ pass     → Git推送者 ── 推送到目标仓库（含失败重试，最多3次指数退避）→ 完成
  └─ fail     → 回退同步执行者（修复同步问题）  max_executions: 3
```

**回路设计：**
- **需求校验回路**：需求接收者（校验）loop → 需求接收者（producer 局部回退，不设 max_executions，用户控制节奏）
- **对抗回路**：差异红队 challenged → **回退到差异分析者**（修订差异分析报告），差异分析者修订后重新触发 FORK（改进评估者 + 差异红队并行重跑），max_executions: 3
- **质量回路**：回归验证者 fail → 同步执行者修复，上限 3 次

**并行设计：**
- 改进评估者与差异红队**并行执行**（FORK + JOIN），提升效率
- 改进评估者从"价值"维度评估差异（哪些值得同步），差异红队从"完整性"维度审查差异分析（是否有遗漏/误判）
- 两者互补不冗余：评估者关注"应该同步什么"，红队关注"分析是否完整准确"
- **JOIN 条件**：改进评估者 confirmed 且 差异红队 confirmed → 汇入平台适配者；若差异红队 challenged，则不进入 JOIN，而是回退到差异分析者

**对抗回路详细说明：**
- 差异红队 challenged → 差异分析者（backward 边，max_executions: 3）
- 差异分析者收到红队对抗报告后，修订差异分析报告（补充遗漏文件、修正误分类）
- 修订后的差异分析报告重新触发 FORK，改进评估者和差异红队**同时重跑**
- 改进评估者基于修订后的差异分析报告重新分类评估，产出新的改进评估报告
- 若差异红队再次 challenged，再次回退（计入 max_executions 计数）
- 超过 3 次后，backward 边被 router 掐断，流水线标记异常终止

**终态设计：**
- 回归验证者 pass → Git推送者执行推送 → 完成
- Git推送者作为终态角色，整合全链路产出（差异报告 + 改进评估报告 + 红队报告 + 适配方案 + 变更摘要 + 验证报告），产出最终推送报告
- Git推送者内置推送失败重试机制（最多 3 次指数退避：1s/2s/4s），重试耗尽后标记失败

## 五、对抗性要求

**明确引入对抗角色：差异红队（第 3 号角色）**

差异红队的对抗维度（5 个维度，每个维度含具体检测项）：

| 维度 | 挑战内容 | 具体检测项 | 判定标准 |
|------|---------|-----------|---------|
| **文件覆盖完整性** | 差异分析是否覆盖了全部核心组件文件？ | ① `engine/scripts/` 下 13 个 `.py` + 4 个平台脚本是否全覆盖？② `engine/sdk/` 下 4 个文件是否全覆盖？③ `engine/schemas/` 下 4 个 schema 文件是否全覆盖？ | 对比文件列表，遗漏文件数 = 0 → 通过 |

| **平台差异识别** | 是否正确区分了平台特定文件？ | ① `.sh` 文件（Mac 专用）是否被误标为"改进"？② `.cmd` 文件（Win 专用）是否被误标为需要从 Mac 同步？③ 平台特定代码块（如 `os.name == 'nt'` 分支）是否被正确识别？ | `.sh`/`.cmd` 文件分类正确率 = 100% |
| **隐藏兼容性问题** | 差异中是否存在隐藏的平台兼容性问题？ | ① Mac 路径硬编码（如 `/Users/`、`/tmp/`）是否被检出？② bash 特有语法（如 `$()`、`&&`）在 Python 代码中的引用是否被检出？③ Unix 权限位设置（如 `chmod`）是否被检出？④ 硬编码的 `python3` vs `python` 调用是否被检出？ | 隐藏兼容性问题检出率 ≥ 90% |
| **变更影响范围** | 差异分析是否评估了每个变更的影响范围？ | ① 每个差异项是否标注了受影响的下游组件？② compiler.py 变更是否标注影响编排链路？③ sdk.py 变更是否标注影响 SDK 接口？④ schema 变更是否标注影响 Gate 校验？ | 每个差异项有影响范围标注 |

**对抗路径：**
- 差异红队 verdict = `confirmed`（通过）→ 汇入平台适配者（JOIN，与改进评估者同时到达）
- 差异红队 verdict = `challenged`（挑战成立）→ **回退到差异分析者**（修订差异分析报告），max_executions: 3。差异分析者修订后重新触发 FORK，改进评估者和差异红队并行重跑

## 六、验收标准

以下标准均为**可证伪的二元判定**（通过/不通过）：

- [ ] **AC-1**：APP 包含 ≥ 8 个角色（含 producer 入口 + 差异红队对抗角色）

- [ ] **AC-2**：app.yaml 编译后 DAG 可达（所有角色从 producer 入口可达，所有角色可达"完成"终态）
  - **证伪方式**：存在孤立角色或不可达终态 → 不通过

  - **证伪方式**：diff(engine/scripts/*.py 列表, 差异报告中列出的文件) ≠ ∅ → 不通过

- [ ] **AC-6**：差异分析报告覆盖 `engine/schemas/` 全部文件（4 个 schema 文件）
  - **证伪方式**：任一 schema 文件未在差异报告中出现 → 不通过

### 6.3 平台适配

- [ ] **AC-7**：同步设计文档中每个待同步改进项均有平台适配方案

## 七、文档层级（第七要素）

本节描述目标 APP（engine-win-sync-builder）的**文档分层结构**。需明确文档类型、依赖关系、文档层与执行层的关系，以及每层的审阅/对抗安排。

> **概念区分**：**文档层** = APP 运行时产出的过程文档和最终报告（记录同步过程和结果）；**执行层** = APP 自身的角色流水线（需求→Win代码获取→分析→对抗→评估→适配→同步→验证→推送）。本节划清这两层并描述它们的映射关系。

### 7.1 文档类型列表

目标 APP 产出的文档按职责分为 **5 大文档类型**：

| 类型代号 | 文档类型 | 典型文档 | 说明 |
|---------|---------|---------|------|
| **L0 需求层** | 需求文档 | 00-需求描述.md | 同步需求文档：目标仓库、Win 版克隆路径、同步范围、排除规则 |
| **L1 分析层** | 差异分析文档 + 改进评估文档 | outputs/差异分析报告.json, outputs/改进评估报告.json, outputs/差异红队-对抗报告.json | 差异分析报告（逐文件对比结果：新增/修改/删除清单）+ 改进评估报告（差异分类结果、待同步改进清单、同步优先级）+ 红队对抗报告（完整性/准确性 findings） |
| **L2 设计层** | 同步设计文档 | outputs/同步设计文档.json | 基于 L1 改进评估报告 + 红队对抗报告，产出待同步改进清单 + 每项的平台适配方案 + 执行顺序 |
| **L3 实施验证层** | 实施与验证文档 | outputs/变更摘要.json + outputs/回归验证报告.json | 变更摘要（实际修改的文件和内容）+ 回归验证报告（语法/编译/DAG/Schema/幂等性/版本号 检查结果） |
| **L4 推送层** | 推送报告 | 推送报告.md | 人类可读总览：同步摘要、变更统计、验证结果、推送状态（含重试日志）、回滚指南 |

### 7.2 文档间依赖关系

文档类型之间存在**有向依赖**（上游被下游引用，下游依赖上游产出）。依赖关系呈**有向无环图（DAG）**，不存在循环引用：

```
L0 需求层 (00-需求描述.md)
    │  定义同步范围、Win 版克隆路径、排除规则
    ▼
L1 分析层
    ├── 差异分析报告.json ─────── 依赖 L0（同步范围决定分析范围）
    │       │
    │       ├── 改进评估报告.json ── 依赖 差异分析报告（差异清单决定分类评估）
    │       │       │
    │       └── 差异红队-对抗报告.json ── 依赖 差异分析报告（审查分析完整性）
    │               │
    │               ▼ （challenged 时回退到差异分析报告，修订后重新触发下游）
    ▼
L2 设计层 (同步设计文档.json)
    │  显式依赖 L1 的改进评估报告（待同步改进清单）+ 红队对抗报告（补充遗漏项）
    │  → 筛选最终待同步项并设计适配方案
    ▼
L3 实施验证层
    ├── 变更摘要.json ─────────── 依赖 L2（适配方案决定实施内容）
    │       │
    │       └── 回归验证报告.json ── 依赖 变更摘要（验证实施结果）
    │               │                  + 依赖 L0（版本号一致性检查需比对 Mac 版版本）
    ▼
L4 推送层 (推送报告.md) ──────── 依赖 L0~L3 全部（整合全链路产出）
```

**依赖规则：**
- **需求文档（L0）**是全链路的起点，定义同步范围、Win 版克隆路径和排除规则
- **差异分析报告（L1）**依赖 L0 的范围定义，产出全量差异清单
- **改进评估报告（L1）**依赖差异分析报告的差异清单，对每个差异进行分类评估，产出待同步改进清单和优先级
- **差异红队-对抗报告（L1）**依赖差异分析报告，审查分析完整性；challenged 时回退到差异分析者修订（max_executions: 3）
- **同步设计文档（L2）**显式依赖 L1 的改进评估报告（待同步改进清单）和红队对抗报告（补充遗漏项），设计适配方案
- **变更摘要（L3）**依赖 L2 的适配方案，记录实际执行的代码修改
- **回归验证报告（L3）**依赖 L3 变更摘要（验证修改后的引擎正确性）和 L0（版本号一致性检查需比对 Mac 版版本）
- **推送报告（L4）**依赖 L0~L3 全部，整合为人类可读的最终报告
- **禁止循环依赖**：若 A 依赖 B，则 B 不得再依赖 A

### 7.3 文档层与执行层的关系

文档层（产物）与执行层（角色流水线）之间存在明确的**产出映射**：

| 执行层角色 | 产出物（执行层） | 对应的文档层内容 |
|-----------|----------------|-----------------|
| 需求接收者 | 00-需求描述.md | → L0 需求层（含 Win 版克隆路径、commit hash） |
| 差异分析者 | outputs/差异分析报告.json | → L1 分析层 |
| 改进评估者 | outputs/改进评估报告.json | → L1 分析层（差异分类结果、待同步改进清单、同步优先级） |
| 差异红队 | outputs/差异红队-对抗报告.json | → L1 分析层对抗审查（决定分析是否通过） |
| 平台适配者 | outputs/同步设计文档.json | → L2 设计层（基于改进评估报告 + 红队报告） |
| 同步执行者 | outputs/变更摘要.json | → L3 实施验证层 |
| 回归验证者 | outputs/回归验证报告.json | → L3 实施验证层（含幂等性检查、版本号一致性检查） |
| Git推送者 | 推送报告.md | → L4 推送层（含推送重试日志） |

**界限原则（文档层与执行层界限分明）：**
1. **执行层过程产物 ≠ 文档层最终成果**：差异分析报告/改进评估报告/同步设计文档/验证报告等是"过程产物"，存在 `outputs/` 目录；推送报告.md 是"最终成果"，存放在 workspace 根目录
2. **对抗角色只产出审查报告**：差异红队产出对抗报告（`outputs/差异红队-对抗报告.json`），不直接修改差异分析报告或同步设计文档。challenged 时通过 backward 边回退到差异分析者，由差异分析者修订
3. **回退时通过 carries 传递上下文**：回归验证者 fail → 同步执行者时，carries 自动注入验证报告，同步执行者据此修复；差异红队 challenged → 差异分析者时，carries 自动注入对抗报告，差异分析者据此修订

### 7.4 每层审阅 / 对抗角色安排

| 文档层 | 主要风险 | 审阅角色 | 对抗角色 | 验证重点 |
|--------|---------|---------|---------|---------|
| **L0 需求层** | 范围不明确、排除规则缺失、Win 版克隆失败 | 需求接收者（校验） | —（producer 自动校验） | 同步范围明确、目标仓库地址有效、Win 版克隆成功 |
| **L1 分析层** | 文件遗漏、差异误判、分类错误 | 改进评估者（分类校验） | **差异红队（完整性对抗，重点）** | 文件覆盖率 100%、差异分类准确、改进评估报告完整 |
| **L2 设计层** | 适配方案遗漏、平台兼容性问题 | 平台适配者（自检） | —（红队 findings 已在 JOIN 时整合） | 每项有适配方案、平台兼容性已评估、L1→L2 依赖完整 |
| **L3 实施验证层** | 同步错误、引擎功能损坏、幂等性违反 | 回归验证者 | —（验证者本身就是审阅角色） | 语法/编译/DAG/Schema/幂等性/版本号 全通过 |
| **L4 推送层** | 推送失败、报告不完整 | Git推送者（自检+重试） | — | 推送成功（含重试日志）、报告含变更摘要 |

**对抗强度说明：**
- L1 分析层是**对抗重点**（差异红队的 5 个维度专门针对这一层，challenged 时回退到差异分析者修订，max_executions: 3）
- L3 实施验证层以**回归验证者**的系统检查为主（语法/编译/DAG/Schema/幂等性/版本号 六维验证）
- 其他层以角色自检和 producer 自动校验为主

13. **文档层级为强制要素**（第七要素）：必须定义 L0~L4 五大文档类型、有向无环依赖关系，并明确文档层与执行层界限
