# 高质量 APP 产出原则

> 注入目标：假设提出者、算法实现者、实验执行者、结果分析者、基线评估者、管线优化者
> 用途：为本 App 全部 6 个角色（M1~M6）提供科研闭环质量底线——这不是格式规范，而是让每轮迭代产出"可信、可追溯、无静默错误"科学结果的思想标准

## 目的

逆散射算法研究的核心价值流是**科研闭环**：假设 → 验证 → 分析 → 新假设。每一轮迭代的产出（代码 diff / 实验结果 / 三件套指标 / Δ 基线对比）都是下游角色的输入，最终汇聚为科学结论。如果任一角色把精力浪费在"锁怎么抢""schema 怎么校验""别人怎么配合我"上，真正的科研核心能力（算法改进推理 / 静默错误识别 / 改进信号提炼）就会被挤占——产出质量下降。

本原则回答一个根本问题：**什么样的科研迭代产出是"好的产出"？** 答案不是"文件写完的产出"，而是**"让每个角色都能专注于自己核心能力的产出"**。

> 科研闭环的编排（M1→M2→M3→M4→M5→M1）是为"专注"服务的。真正的敌人是协议税（锁/schema/配置加载）对角色核心能力的污染，以及静默错误对科学结论的隐形破坏。

## 核心准则

### 准则 1：重点意识——核心能力占比 ≥ 60%

**Why 推理链**：
科研角色的认知资源是有限的。如果假设提出者把精力花在"hypothesis_chain.json 的五字段 schema 怎么填"，而非"为什么 B-spline K 调大会改善 cos θ"，核心科研推理就被协议细节淹没。认知负荷理论（Cognitive Load Theory）指出，外在认知负荷（协议/机制）会挤占内在认知负荷（算法改进推理）。**每个角色的产出中，核心能力内容应占 ≥ 60%**。

**When not**：
- 角色首次执行（冷启动）时，需要理解 schema/协议——但这应来自注入的检查清单（资产），不是角色自己推理。

**省略后果**：
- M4 结果分析者的产出中 60% 是"sanity.json 怎么读"，仅 40% 是"三件套怎么算/静默错误怎么识别" → 分析报告质量下降，静默错误漏检风险上升。

**怎么做**：
对每个角色的产出逐条分类：[科研能力]（假设推理/算法实现/指标计算/基线对比）vs [协议税]（schema/锁/配置加载/dispatch）。核心能力占比 = 科研能力行数 / 总行数 ≥ 60%。

### 准则 2：协议税意识——协议的事归协议，科研的事归角色

**Why 推理链**：
本 App 有协议约束（pipline 算法目录写权限、config_snapshot.json schema、mphserver 单实例约束、git tag 快照）。这些是科研闭环的"基础设施"，不是角色的"核心能力"。如果每个角色都在产出中重复解释协议原理，协议内容会在 6 个角色间重复传播——维护噩梦，且与核心能力无关。

**When not**：
- 角色执行时**需要遵守**协议（如 M2 只改算法目录、M3 写 config_snapshot.json + git tag），但**不需要在产出中重新解释协议原理**——协议规则已固化为各角色 skill.md 中的自检项，角色"对照打勾"即可。

**省略后果**：
- 每个角色的报告都花篇幅解释 mphserver 信号量为什么 ≤ 1 → 重复信息污染产出，真正的研究结论被埋没。

**怎么做**：
产出中出现以下内容即为协议税，应消除或移到对应知识文档：
- ❌ "config_snapshot.json 必须含七字段因为…" → skill.md 自检项已列，角色对照填写即可
- ❌ "mphserver 单实例是因为 COMSOL license 限制…" → 实验执行手册已解释，角色遵守即可
- ✅ "本次实验 cos θ = 0.985，相比基线 0.9929 下降 0.008，原因分析…" → 核心能力，必须保留

### 准则 3：职责聚焦——一个角色一个核心能力

**Why 推理链**：
本 App 的 6 个模块各有单一核心能力：M1 假设生成、M2 算法实现、M3 实验执行、M4 结果分析、M5 基线评估、M6 管线优化。一个角色承担多类不相关职责时，其产出必然臃肿，核心能力被稀释（上帝角色反模式）。科研闭环的价值在于"每个阶段由专注该阶段的角色负责"，如果角色自己都不专注，闭环就失去了拆解的意义。

**When not**：
- M4 结果分析者既做"健全性校验"又做"三件套计算"——这看似两类职责，实则是同一核心能力（"从实验产出中提取可信指标"）的前后两步，健全性校验是三件套计算的前置守门人，不构成职责拆分。

**省略后果**：
- M6 管线优化者同时做"算法假设"和"管线补丁" → 违反 REQ-011 AC1 职责限定，算法研究与管线工程混杂，关注点分离失效。

**怎么做**：
对每个角色问：**能用一句话写出它的核心能力吗？**
- M1 = "把改进直觉转化为结构化可追溯假设记录" ✓
- M2 = "把假设转化为 pipline 算法目录的可执行代码 diff" ✓
- M4 = "从实验产出中提取三件套指标并拦截静默错误" ✓
- 如果一句话写不完 → 承担了多类职责 → 检查是否越界。

### 准则 4：独立视角价值——分析/评估角色因"无滤镜"而有独立价值

**Why 推理链（认知科学基础）**：
科研产出者天然有 3 种认知偏差：①确认偏差——倾向于寻找支持自己假设的证据（"我调的 K 值应该改善 cos θ"）；②锚定效应——被已有设计锚定（"用了 Born 近似就不会想 Full Maxwell 可能更好"）；③知识诅咒——自己知道的东西难以想象"不知道会怎样"。

M4 结果分析者和 M5 基线评估者的核心能力 = **无滤镜的独立视角**。M4 对 M3 实验产出做健全性校验，能拦截 mphserver 返回的"数值看似合理但物理错误"的静默结果——这种错误 M3（执行者）自己察觉不到，因 M3 的关注点是"实验跑通"而非"结果是否物理正确"。**产出者的自检无法替代独立检查**——这是 M4/M5 存在的根本理由，不是冗余。

**When not**：
- M5 评估 M4 分析结果时，M4 的分析报告已经是"半独立"产出（M4 独立于 M3），但 M5 的基线对比仍是必要的二次独立校验——因为 M4 可能因值域断言阈值设置不当而放过边界错误。

**省略后果**：
- 去掉 M4 健全性校验 → NaN/Inf/越界结果无检测进入 M5 基线对比，exceeds_baseline 判定基于错误数据，研究者产出无效科学结论（比崩溃更危险，因崩溃至少可察觉）。

**怎么做**：
- 信息隔离：M4 inputs = [experiment/ 实验产出物]，不含 M3 执行日志/推理过程；M5 inputs = [experiment/ 分析报告 + baseline 只读资产]，不含 M4 分析推理过程。
- 原则外化：判定依据来自外部资产（基线固化值/健全性校验清单/值域断言），不是角色自己主观推理。

### 准则 5：资产优先——能用清单/基线解决的不用编排

**Why 推理链**：
资产（基线/检查清单/git 版本控制）的成本曲线是"一次性固化，之后每轮迭代复用成本趋近于 0"；编排（每轮手动检查）的成本是"每次迭代都付"。三件套基线（A12=5/7 / C01=4/6 / cos θ=0.9929）固化在 baseline/metrics_baseline.json（只读不可漂移），M5 每轮只需读基线做减法——这是资产解。健全性校验的 NaN/Inf 检测内联在 M4 的 skill.md 中——这是清单资产解。

**怎么做**：
设计任何机制时，按此顺序决策：
1. 能用**检查清单**解决？（如 NaN/Inf 检测）→ 沉淀为 skill.md 自检项
2. 能用**固化基线**解决？（如 Δ 对比基准）→ 沉淀为只读资产
3. 必须动态决策？（如"是否启动新假设"）→ 用编排解决，但最小化

### 准则 6：基线只读 + pipline 版本控制

**Why 推理链**：
本 App 区分两类资产：
- **固化基线**（只读）：baseline/metrics_baseline.json（三件套基线值）——研究者维护，M5 只读消费，不可修改。
- **持久化代码**（pipline）：COMSOL/pipline/ 是科研资产，所有角色直接操作，git 版本控制保证可追溯。
- **Run 产出**（每轮迭代）：hypothesis_chain.json 条目 / 代码 diff / experiment 子目录 / 分析报告 / Δ 对比报告——由 M1~M5 产出。

**省略后果**：
- M2 修改 baseline/metrics_baseline.json → 基线漂移，所有历史 Δ 对比失效。
- pipline 代码无 git 版本控制 → 改动不可追溯，跨实验对比失去共同基准。

### 准则 7：静默错误是头号敌人——健全性校验是不可妥协的质量底线

**Why 推理链**：
逆散射场景的独特风险是 mphserver 可能返回"数值看似合理但物理错误"的结果（网格畸变 / license 降级 / B-spline K=500 病态 / 局部极值）。这种**静默错误**比崩溃危险得多——崩溃至少会被察觉并中止，静默错误会一路传播到 M5 基线对比，研究者基于错误指标产出无效科学结论。健全性校验层（IF-8：NaN/Inf 必选 + 值域断言必选 + 可重复性/benchmark 可选"至少其一"invariant）是拦截静默错误的最后防线。

**When not**：
- result_status 已判定为 EMPTY/DIVERGED/NOT_CONVERGED 时，三件套不计算或降级处理——此时结果已知异常，不需要健全性校验"再确认"。

**省略后果**：
- 健全性校验被跳过或两开关同时关闭 → 静默错误无检测传播，科研结论无效（比崩溃更危险）。

**怎么做**：
- M4 入口前置 sanity_check.m，在 compute_three_piece.m 之前强制执行且通过。
- 健全性校验失败即阻断，三件套不计算。
- 校验结果在 analysis_report.md 中记录。

## 编排三问（每个角色产出前必须回答）

任何产出开始前，必须对照回答：
1. **这次产出服务的是哪个科研目的？**（假设验证/算法改进/指标可信度/改进方向——说不清楚就是"为产出而产出"）
2. **这个目的能不能不用手动推理达成？**（能用基线/清单/schema 解决吗？）
3. **这是角色核心能力，还是协议约束？**（前者保留并深化，后者对照清单遵守即可）

## 判别清单

每个角色产出本职前，逐项核对：
- [ ] 产出中核心科研能力内容占比 ≥ 60%？（准则 1）
- [ ] 产出中不包含协议原理重复解释（config_snapshot schema/mphserver 约束的"为什么"）？（准则 2）
- [ ] 能用一句话写出本角色核心能力，无越界承担其他角色职责？（准则 3）
- [ ] 分析/评估角色的 inputs 不含上游角色的推理过程（信息隔离）？（准则 4）
- [ ] 判定依据来自外部资产（基线/清单/值域断言），非主观推理？（准则 4）
- [ ] 能用清单/基线/schema 解决的未用手动编排？（准则 5）
- [ ] baseline/metrics_baseline.json 只读未改，pipline 代码通过 git 版本控制管理？（准则 6）
- [ ] NaN/Inf 检测 + 值域断言已执行且通过？（准则 7）

## 反模式速查

| # | 反模式 | 症状 | 违背原则 |
|---|--------|------|---------|
| 1 | 协议税污染 | 分析报告 60% 篇幅解释 config_snapshot schema 原理 | 协议税意识 |
| 2 | 角色越界 | M6 同时做算法假设和管线补丁 | 职责聚焦 |
| 3 | 自检替代独立检查 | M3 自己判断结果是否物理正确，跳过 M4 健全性校验 | 独立视角价值 |
| 4 | 基线漂移 | 某轮迭代修改了 baseline/metrics_baseline.json | Build-Run 分层 |
| 5 | 静默错误传播 | NaN/Inf 检测被跳过，NaN 结果进入 M5 对比 | 静默错误底线 |
| 6 | 手动重算基线 | 每轮手动重算三件套基线而非读固化资产 | 资产优先 |

## 一句话总结

> **好的科研迭代产出不是"文件写完的产出"，而是"让每个角色专注核心能力、静默错误被拦截、基线不漂移"的产出。协议税是专注的头号敌人，固化基线/清单是质量提升的主力，独立校验是分析/评估角色存在的根本理由。**
