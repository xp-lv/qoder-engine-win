# 管线能力契约规范

## 1. 目的

本文档定义管线能力契约的格式规范，供管线匹配者、管线重构者、算法实现者使用。管线的所有能力通过 **pipeline.json** 和 **pipeline_registry.json** 两层结构声明。

## 2. 两层结构

| 文件 | 位置 | 作用 |
|------|------|------|
| `pipeline_registry.json` | `COMSOL/` 根目录 | 全局注册表，注册所有代际，声明每代的 abs_path 和能力摘要 |
| `pipeline.json` | 每代管线根目录 | 该代管线的自描述，含完整能力声明 + 目录结构 + 关键脚本索引 |

### 绝对路径（运行时读取）
- 注册表：`d:\ZJU\PROJECT\2026-07-02-qoder-engine\COMSOL\pipeline_registry.json`
- gen1 自描述：`d:\ZJU\PROJECT\2026-07-02-qoder-engine\COMSOL\pipline\pipeline.json`

## 3. 能力契约字段定义

能力契约位于 pipeline.json 和 registry 的 `capabilities` 字段：

### forward（正演能力）
| 字段 | 类型 | 说明 |
|------|------|------|
| `method` | string | 正演方法（如 `COMSOL_mphinterp`, `neural_surrogate`） |
| `max_freq_hz` | number | 最高支持频率 |
| `nonuniform_bg` | bool | 是否支持非均匀背景场 |
| `bg_types` | array | 支持的背景场类型（如 `planewave`, `gaussian`） |

### adjoint（伴随能力）
| 字段 | 类型 | 说明 |
|------|------|------|
| `method` | string | 伴随方法（如 `analytical_maxwell`, `pytorch_autograd`） |
| `differentiable` | bool | 是否可微分（端到端梯度） |

### parameterization（参数化能力）
| 字段 | 类型 | 说明 |
|------|------|------|
| `supported` | array | 支持的参数化类型（如 `voxel`, `b-spline`, `uniform`, `latent`） |
| `default` | string | 默认参数化类型 |
| `max_control_points` | number | 最大控制点数（B-spline 专用） |

### constraints（约束支持）
| 字段 | 类型 | 说明 |
|------|------|------|
| `phantom_prior` | bool | 是否支持仿体先验 |
| `tikhonov` | bool | 是否支持 Tikhonov 正则化 |
| `tv_regularization` | bool | 是否支持 TV 正则化 |
| `nonuniform_bg` | bool | 是否支持非均匀背景场约束 |

### metrics（评估指标支持）
| 字段 | 类型 | 说明 |
|------|------|------|
| `cos_theta` | bool | 是否支持 cos θ 指标 |
| `f_cheb` | bool | 是否支持 Chebyshev 残差 |
| `pass_count` | bool | 是否支持 PASS 计数 |

## 5. 匹配规则（管线匹配者使用）

研究者假设中的 `pipeline_requirement` 字段与管线能力逐一比对：

1. `forward.method` — 研究者声明的正演方法必须与管线 capabilities.forward.method 匹配
2. `parameterization` — 研究者声明的参数化类型必须在 capabilities.parameterization.supported 列表中
3. `constraints` — 研究者声明的约束必须全部在 capabilities.constraints 中为 true
4. 如有多代管线匹配，优先选 status=stable 的

**匹配结果**：
- `full_match`：所有维度满足
- `partial_match`：核心维度满足，次要维度不满足（仍可执行）
- `no_match`：关键维度不满足 → 触发管线重构

## 6. 运行时 vs 编译时的信息来源

| 信息 | 来源 | 时机 |
|------|------|------|
| 能力契约格式规范 | 本文档（knowledge 注入） | 编译时 |
| gen1 能力基线 | 本文档（knowledge 注入） | 编译时 |
| 最新管线注册表 | `COMSOL/pipeline_registry.json`（skill.md 绝对路径） | 运行时 |
| **管线使用方法** | 各代 `pipeline.json` 的 `usage` 字段（运行时读取） | **运行时** |

> **关键设计**：管线的具体使用方法（语言、config格式、调用命令、参数索引）不在本文档中硬编码，
> 而是存在于每代管线的 `pipeline.json` 的 `usage` 字段中。
> 这样新建 gen2 时，算法实现者和实验执行者无需更新 knowledge——只需读取新管线的 usage 字段即可自适应。

## 7. 角色获取管线使用方法的通用流程

所有需要操作管线的角色（算法实现者、实验执行者、管线维护者）遵循同一流程：

```
步骤 1：读取 outputs/管线匹配报告.json → 获取 matched_path
步骤 2：读取 {matched_path}/pipeline.json → 获取 usage 字段
步骤 3：按 usage 中的指引操作
```

### usage 字段结构（每代管线自定义）

| 字段 | 说明 | gen1 示例 | gen2 示例（假设） |
|------|------|---------|-----------|
| `language` | 管线使用的编程语言 | MATLAB | Python |
| `config_file` | 参数配置文件路径 | config/config.m | config/config.yaml |
| `config_format` | 配置文件格式说明 | MATLAB struct (p.xxx) | YAML key: value |
| `entry_command` | 实验调用命令 | run_experiment('plugin') | python run_experiment.py --plugin |
| `runtime_requirements` | 运行时依赖 | COMSOL Server port 2036 | GPU + COMSOL training data |
| `key_params` | 关键参数索引 | p.n_cx, p.weight_strategy... | model.latent_dim, train.lr... |
| `param_modification_guide` | 参数修改指南 | 修改 config.m 中 p 结构体 | 修改 config.yaml 中对应 key |
| `plugin_dir` | 插件目录 | algorithm/ | plugins/ |
| `plugin_signature` | 插件入口函数签名 | function state = run_inversion(...) | def run_inversion(...) -> dict |
| `plugin_params` | 插件参数说明 | model/voxel/lc/grid/p | model/voxel/lc/grid/cfg |
| `state_fields` | state 返回值字段 | converged/iteration/residual/history_J_hyp | 同左（跨代统一） |
| `execution_steps` | 执行流程描述 | 9步（setup→mphstart→...→三件套） | 5步（load_data→forward→loss→backward→metrics） |

> `state_fields` 是跨代统一的接口约定——无论 gen1 还是 gen2，插件返回的 state 必须包含 converged/iteration/residual/history_J_hyp。

## 8. 管线维护者与重构者的边界

| | 管线维护者 | 管线重构者 |
|---|---|---|
| 触发方式 | 手动（manual） | 汇聚裁决 needs_pipeline |
| 改变能力契约？ | **否** | **是** |
| 更新 registry？ | **否** | **是** |
| 创建新代际？ | **否** | **是** |
| 更新 usage 字段？ | **否**（除非版本适配） | **是**（新建代际时必须写 usage） |
| 典型操作 | bug修复、性能优化、版本适配 | 新增插件、新建 gen2 管线 |

> 管线维护者更新 usage 的唯一场景：版本适配（如 COMSOL 6.2→6.3 导致 API 变化），
> 只更新 usage 中的版本号和 runtime_requirements，不改变核心操作流程。

## 9. 新建管线必须遵循的 pipeline.json 规范（管线重构者必读）

管线重构者在创建新代际管线时，必须在管线根目录下创建 `pipeline.json`，且必须包含以下顶层字段：

### 必须包含的顶层字段

| 字段 | 必填 | 说明 |
|------|:----:|------|
| `generation` | ✓ | 代际标识（如 `gen2_hybrid`），必须与 registry 中的 key 一致 |
| `version` | ✓ | 管线版本号（如 `1.0.0`） |
| `name` | ✓ | 管线名称 |
| `status` | ✓ | 状态（`experimental` / `stable`） |
| `abs_path` | ✓ | 管线根目录的绝对路径 |
| `capabilities` | ✓ | 能力契约（§3 中定义的全部子字段） |
| `plugins` | ✓ | 至少一个插件的声明（含算法名、参数化类型、入口路径） |
| `usage` | ✓ | 使用指南（§7 中定义的全部子字段） |
| `directories` | ✓ | 目录结构映射 |
| `entry_script` | ✓ | 实验入口脚本的绝对路径 |

### capabilities 必须包含的子字段

```json
"capabilities": {
  "forward": {"method": "...", "description": "..."},
  "adjoint": {"method": "...", "differentiable": true/false},
  "parameterization": {"supported": [...], "default": "..."},
  "constraints": {...},
  "metrics": {"cos_theta": true, "f_cheb": true, "pass_count": true}
}
```

> **铁律**：`metrics` 必须全部为 true——跨代统一的评估指标接口。无论 gen1 还是 gen2，
> 实验产出必须支持 cos θ / F_cheb / PASS 计数，否则基线评估者无法处理。

### usage 必须包含的子字段

```json
"usage": {
  "language": "...",
  "config_file": "...",
  "config_format": "...",
  "entry_command": "...",
  "entry_script": "...",
  "runtime_requirements": "...",
  "key_params": {...},
  "param_modification_guide": "...",
  "plugin_dir": "...",
  "plugin_signature": "...",
  "plugin_params": {...},
  "state_fields": {
    "converged": "...",
    "iteration": "...",
    "residual": "...",
    "history_J_hyp": "..."
  },
  "execution_steps": [...]
}
```

> **铁律**：`state_fields` 必须包含 converged / iteration / residual / history_J_hyp 四个字段——
> 这是跨代统一的插件返回值接口。无论管线用什么语言实现，插件返回的 state 必须能提取这四个指标。

### 同时必须更新的外部文件

| 文件 | 操作 |
|------|------|
| `COMSOL/pipeline_registry.json` | 在 `generations` 中添加新代际条目，更新 `latest` 字段 |

### 新建管线后必须验证的闭环

管线重构者创建新管线后，需在管线重构报告中声明以下验证项：

```
✓ pipeline.json 已创建，包含所有必填字段
✓ capabilities.metrics 全部为 true
✓ usage.state_fields 包含四必须字段
✓ 至少一个插件已创建（含入口函数）
✓ pipeline_registry.json 已注册新代际
✓ 新管线的 capabilities 覆盖了汇聚裁决报告中的 pipeline_gap
```
